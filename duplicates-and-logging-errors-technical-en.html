Duplicates and logging errors, for programmers

At-least-once delivery and deduplication keys, event time versus processing time with watermarks, a model for clock drift and its estimation from the lower envelope with Theil-Sen, GPS jump detection with implied speeds, frozen sensors and physical cross-checks. With a from-scratch module verified against pandas, SciPy and scikit-learn, a simulated day of telemetry and an example worked by hand.

Summary

  • Telemetry protocols guarantee at-least-once delivery: duplicates are part of the design. They are removed with a key over the content, never over the transport id.
  • Every computation that depends on order (distances, trips, transitions) is done in event time. Arrival time is only useful for measuring latencies and clock drift.
  • Since network latency is non-negative, the lower envelope of estimates the clock error. A robust fit on that envelope recovers it; a least-squares fit on all the messages does not.
  • GPS jumps: a point is fake if the implied incoming and outgoing speeds exceed a physical threshold. Frozen sensors: constant-value runs while moving.
  • Nothing gets deleted: quality columns are added and the original is kept.
raw→ deduplicate→ sort by event→ correct clock→ flag jumps→ flag frozen

§1 · Duplicates

At-least-once delivery and deduplication keys

An onboard device sends a message and waits for an acknowledgment (ACK). If the ACK is lost, it can't know whether the message arrived, so it resends it. This is the at-least-once semantics of MQTT QoS 1, of most proprietary protocols over TCP/UDP, and of queues like Kafka without transactions. "Exactly once" doesn't exist on the network. It is built with idempotence at the receiver: processing the same message twice must give the same result as processing it once.

The deduplication key must identify the fact, not the send:

  • The id assigned by the server, the queue offset or the arrival time change with every resend: they are useless as keys.
  • If the device stamps its own sequence number, that's the best key. Watch out for reboots (it goes back to 0) and counter overflow.
  • In streaming, deduplication needs state: a set of seen keys with an expiry longer than the maximum delay of a resend (in the simulation, 90 s; in reality, hours if the device buffers in memory).
  • Near-duplicates: some devices regenerate the message when resending it (with a differently rounded timestamp, or recomputing a field). There you compare with tolerance: same device, and same position within a few meters.

In the simulation, 5% of the messages arrive twice. The distance, once sorted, doesn't change (the segment between the two copies measures 0), but the time above 80 km/h inflates from 156 to 163.5 minutes.

§2 · Order

Event time, processing time and watermarks

Every message has two times: the event time (, when it happened) and the processing time (, when it was received). Devices buffer messages when there's no coverage and send them once it comes back, usually interleaved with the new ones. Sorting by arrival produces zigzag trajectories: in the simulation, 1,221 km instead of 544.

In a batch system it's enough to sort by event time before computing. In a streaming system you have to decide how long to wait for stragglers. A watermark asserts "no more events earlier than will arrive". The simplest choice is :

  • Large : more complete but later results.
  • Small : fast results, but messages that arrive after the watermark must be discarded or used to correct results already emitted (allowed lateness in Apache Beam and Flink).

The delay distribution is highly skewed: almost all messages arrive within seconds and a few, after a coverage gap, within tens of minutes. A high percentile (p95, p99) isn't enough to choose : what matters is what to do with the tail.

§4 · Positions

Distances, implied speeds and jumps

The distance between two positions (latitude , longitude ) on a sphere of radius km is the haversine formula:

Its error against the WGS84 ellipsoid is under 0.5%, more than enough for cleaning. The implied speed between consecutive messages is . An isolated jump forces both a fast entry and a fast exit, so point is flagged if

The worst one (largest sum of the two speeds) is removed, everything is recomputed and the process repeats, because two jumps in a row hide each other. Requiring both conditions avoids flagging the good point next to a jump. With a very small (two messages in the same second) the speed blows up with errors of a few meters: a minimum distance or using acceleration helps.

This rule is the hard version of what a Kalman filter does with a validation gate: discard observations whose normalized innovation squared (NIS) is impossible under the motion model. For very noisy trajectories, the next step is map matching: fitting the sequence to the road network with a hidden Markov model.

§5 · Sensors

Frozen values and physical cross-checks

A frozen sensor repeats its last value. It is detected as a run (run length) where for at least minutes, with a condition that makes a constant value physically impossible: here, that the odometer advances at least 5 km. Other checks that relate columns:

CheckWhat it reveals
odometer non-decreasingdevice reboots, device swapped between trucks
Δodometer ≈ GPS distance (±5%)GPS jumps, miscalibrated odometer
fuel drops if Δodometer > 0frozen sensor, theft (drop without movement)
CAN speed ≈ GPS implied speedclock offset between sources
RPM = 0 ⇒ speed = 0messages mixed from two devices

A zero rolling variance detects the same thing as run length, but with quantization noise (sensors with few levels) it gives false alarms: has to be set based on the sensor's resolution and expected rate of change.

§6 · Design

Flag instead of delete

Each rule adds a boolean column (es_reenvio, salto_gps, combustible_congelado) and, if it corrects something, a new column (t_corregido) without touching the original. Advantages:

  • You can change a threshold and recompute without re-ingesting.
  • The rate of each flag per device and day is a quality metric: a device with 30% jumps or a clock that drifts 5 minutes a day needs a physical inspection.
  • For a model, "this value is missing because the sensor was frozen" is information (topic 5); an unexplained gap is not.

Order matters: deduplicate before sorting (otherwise the two copies end up together and the order is correct, but the counts aren't); sort before computing speeds; correct the clock before joining with other sources; flag jumps before computing distances.

§7 · From scratch

A verified cleaning module

tele.py

import numpy as np

R_TIERRA = 6371.0088          # mean Earth radius in km (the one scikit-learn uses)

def haversine(lat1, lon1, lat2, lon2):
    p1, p2 = np.radians(lat1), np.radians(lat2)
    dphi, dlmb = p2 - p1, np.radians(lon2) - np.radians(lon1)
    a = np.sin(dphi / 2) ** 2 + np.cos(p1) * np.cos(p2) * np.sin(dlmb / 2) ** 2
    return 2 * R_TIERRA * np.arcsin(np.sqrt(a))

def distancia_total(df):
    return float(np.sum(haversine(df.lat.values[:-1], df.lon.values[:-1], df.lat.values[1:], df.lon.values[1:])))

def quitar_duplicados(df, clave=("t_equipo", "lat", "lon", "vel", "odo")):
    """Key over the content; keeps the copy that arrived first."""
    return df.sort_values("t_servidor").drop_duplicates(subset=list(clave), keep="first")

def velocidad_implicita(df):
    d = haversine(df.lat.values[:-1], df.lon.values[:-1], df.lat.values[1:], df.lon.values[1:])
    return d / np.maximum(np.diff(df.t_equipo.values) / 3600, 1e-9)

def marcar_saltos(df, vmax=160.0):
    """Flags the point whose entry AND exit are above vmax; removes the worst and repeats."""
    df = df.copy(); df["salto_detectado"] = False; idx = np.arange(len(df))
    while True:
        sub = df.iloc[idx]; v = velocidad_implicita(sub)
        malo = np.zeros(len(sub), bool); malo[1:-1] = (v[:-1] > vmax) & (v[1:] > vmax)
        if not malo.any(): break
        score = np.zeros(len(sub)); score[1:-1] = v[:-1] + v[1:]
        peor = int(np.argmax(np.where(malo, score, -1)))
        df.iloc[idx[peor], df.columns.get_loc("salto_detectado")] = True; idx = np.delete(idx, peor)
    return df

def tramos_congelados(t, valor, odo, min_min=30.0, min_km=5.0):
    """Runs of identical value lasting at least min_min minutes while covering at least min_km."""
    t, valor, odo = map(np.asarray, (t, valor, odo)); out = []; i = 0
    while i < len(valor):
        j = i
        while j + 1 < len(valor) and valor[j + 1] == valor[i]: j += 1
        dur = (t[j] - t[i]) / 60
        if dur >= min_min and odo[j] - odo[i] >= min_km:
            out.append((float(t[i]), float(t[j]), float(dur), float(odo[j] - odo[i])))
        i = j + 1
    return out

def theil_sen(x, y):
    x, y = np.asarray(x, float), np.asarray(y, float); i, j = np.triu_indices(len(x), 1)
    ok = x[j] != x[i]; s = np.median((y[j] - y[i])[ok] / (x[j] - x[i])[ok])
    return s, np.median(y - s * x)

def estimar_deriva(t_equipo, t_servidor, ventana_s=1800):
    """Minimum of (arrival - device) per window + Theil-Sen. Returns s/h (real hour), intercept and points."""
    t_equipo = np.asarray(t_equipo, float); d = np.asarray(t_servidor, float) - t_equipo
    b = np.floor((t_equipo - t_equipo.min()) / ventana_s); xs, ys = [], []
    for k in np.unique(b):
        m = b == k; i = np.argmin(d[m]); xs.append(t_equipo[m][i]); ys.append(d[m][i])
    s, c = theil_sen(np.array(xs), np.array(ys))
    return -s * 3600 / (1 + s), c, (np.array(xs), np.array(ys))

§8 · A day of telemetry

The full cleanup, step by step

One truck, from 6:00 to 16:00, one message every 30 s (1,200 facts), with 5% resends, half an hour without coverage whose messages arrive interleaved, a clock that runs 40 s/h fast, 6 GPS jumps of 3 to 8 km and the fuel sensor frozen for two hours.

The final distance (543.4 km) is within 0.1% of the odometer (544.1). The remaining difference comes from measuring in a straight line between positions every 30 s: on curves, the chord is shorter than the arc. With messages every 30 s at 80 km/h (667 m between points) the effect is small, but with messages every 5 minutes it shows and you'd better use the odometer.

§9 · Checklist

Before using telemetry data

  • Both times (device and arrival) are stored, in UTC.
  • Deduplication key over the content or the device sequence, with state that outlives the maximum resend delay.
  • All order-dependent computations done in event time.
  • Clock drift estimated per device and day from the lower envelope; alert if it exceeds a threshold.
  • GPS jumps flagged with incoming and outgoing implied speeds.
  • Frozen runs searched for in every sensor, with a movement condition.
  • Cross-checks: increasing odometer, odometer versus GPS, fuel versus kilometers.
  • Flag columns instead of deletions, and flag rates per device as a quality metric.

§10 · Worked example

From 11 km to 2 km, by hand

Six messages, three logging errors and all the math: distances, duplicate key, order, implied speeds, clock drift with Theil-Sen and a frozen sensor.

The setup. A truck drives for two minutes in a straight line at 60 km/h, from 10:00:00 to 10:02:00. It should log 2 km. The mileage report says 11.

Example map

Two minutes of a truck driving in a straight line at 60 km/h: it should cover 2 km. Six messages arrive, with a resend, one out of order and a GPS jump. We fix each problem by hand and watch the distance go from 11.2 km to 2.0. Then we estimate the clock's lead from three messages and detect a frozen sensor.

  1. The messages as they arrive

    In words

    So we can add things up by hand, the positions are in kilometers on a plane (x to the east, y to the north) instead of latitude and longitude. Device time is counted in seconds since 10:00:00.

    Where does each problem come from?

    The 30 s message arrived late (after the 60 s one) and also twice: 3 and 4 have the same content with different ids. Message 5 should be at (1.5, 0) but the GPS put it at (5, 3). With latitude and longitude you'd use the haversine formula (§4). At these distances it gives the same result as the plane, with a difference under 0.1%.

    In words

    The math

    What it means: 11.15 km for a 2 km trip, more than five times too much. Almost all of it comes from the GPS jump (5.41 + 4.24) and half a kilometer from the disorder (going from 2 to 3 means going backward).

  3. Remove the resend

    In words

    Messages 3 and 4 have different ids but the same device time and the same position. It's the same fact sent twice. We keep the one that arrived first (3).

    The math

    What it means: the distance doesn't change (segment 3→4 measured 0), but now there are 5 messages instead of 6. If we counted messages with speed above zero, or time spent driving, the resend would have inflated it.

  4. Sort by device time

    The math (order 1, 3, 2, 5, 6)

    What it means: the backtracking is gone, but the GPS jump still adds more than 9 km.

  5. Speeds needed and the GPS jump

    In words

    For each pair of consecutive messages, we divide the distance by the time. A point is fake if getting to it and leaving it both require going faster than the threshold (here, 160 km/h). Checking both avoids blaming the good point next to it.

    The math (30 s = 1/120 h)

    Why 160 km/h?

    It has to be clearly above what the truck can do (about 100 km/h on the highway, plus normal GPS error) and below what the jumps require (hundreds or thousands). In this example any threshold between 61 and 508 km/h would do; in the simulated day, between about 100 and 280 km/h, because the smallest jump requires about 290. The widget in idea 4 of the simple version shows what happens if you set it too low.

    What it means: without point 5, the three segments run at 60 km/h and the distance is exactly 2 km. The point isn't deleted: it's flagged as a jump, and its timestamp still tells us the device was working.

  6. The clock's lead

    In words

    For each half hour of the day we take the message that arrived fastest and compute "arrival time minus device time". The network only delays, so that minimum value is almost entirely clock error. Three of those messages:

    The math

    device timearrival − device
    8:00−79.5 s
    12:00−239.5 s
    16:00−399.5 s

    Why the median of the slopes?

    It's the Theil-Sen estimator: the median of the slopes between all pairs of points. If one minimum is contaminated (for example, a half hour in which only delayed messages arrived), a least-squares line would bend and the median wouldn't. With the fleet's 1,200 messages, a least-squares line over all the messages gives −30 s/h, because the delayed ones pull it up. With the lower envelope and Theil-Sen it comes out −40.

    Correcting the stop at device time 11:03:20

    What it means: the stop began around 11:00, before the 11:01 receipt, and the fraud alert goes away. The 2 s difference from the exact time comes from the network's minimum delay (half a second) and from measuring the times with the fast clock itself: negligible for this decision.

  7. The frozen fuel sensor

    In words

    Tank readings every 10 minutes together with the odometer. We look for stretches where the value doesn't change for at least 30 minutes while the truck covers at least 5 km.

    The data and the math

    min01020304050
    %63.162.462.462.462.462.4
    km0918283747

    Why require kilometers?

    With the truck stopped, it's normal for the fuel not to change. Without the 5 km condition, every long stop would look like a broken sensor. Conversely, a truck that burns 30 L per 100 km from a 600 L tank drops 5% in 100 km: in 38 km, the level should have dropped almost 2%, and a sensor with one decimal place would notice.

    What it means: minutes 10 to 50 are flagged as a frozen reading. For a fuel-consumption model, that stretch isn't "38 km without using fuel" but "38 km with no fuel data".

import numpy as np, pandas as pd
from tele import theil_sen, tramos_congelados

m = pd.DataFrame(dict(id=[1, 2, 3, 4, 5, 6], t_equipo=[0, 60, 30, 30, 90, 120],
                      x=[0, 1.0, 0.5, 0.5, 5.0, 2.0], y=[0, 0, 0, 0, 3.0, 0]))
dist = lambda d: float(np.hypot(np.diff(d.x), np.diff(d.y)).sum())
print(round(dist(m), 3))                                            # 11.151
m = m.drop_duplicates(subset=["t_equipo", "x", "y"])               # id 4 dropped
m = m.sort_values("t_equipo"); print(round(dist(m), 3))            # 10.243
v = np.hypot(np.diff(m.x), np.diff(m.y)) / (np.diff(m.t_equipo) / 3600)
print(v.round(0))                                                   # [ 60.  60. 600. 509.]
m = m[~((np.r_[0, v] > 160) & (np.r_[v, 0] > 160))]; print(round(dist(m), 3))   # 2.0

s, c = theil_sen(np.array([8.0, 12.0, 16.0]), np.array([-79.5, -239.5, -399.5]))
print(s, c)                                                          # -40.0 240.5
te = 11 + 3 / 60 + 20 / 3600
print(round((te + (s * te + c) / 3600 - 11) * 3600, 1))              # -1.7 (s relative to 11:00:00)

What would change in a real system

  • Latitude and longitude instead of the plane, with haversine.
  • Many devices at once: the duplicate key and the clock drift, always per device.
  • In streaming: a watermark to decide when to consider the two minutes closed, and a correction if message 3 arrives afterward.
  • Thresholds per vehicle type: a motorcycle or a van can go faster than a truck.
